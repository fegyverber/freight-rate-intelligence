# ML: признаки, обучение и пакетный прогноз

Основная точка входа — `run_ml(connection, as_of, output_dir, seed=20261026,
iterations=500, thread_count=2)` в `ml/pipeline.py`. Соединение предоставляет
`etl.db.connect()`; тот же модуль конфигурации используется в самостоятельном запуске:

```bash
python -m ml.pipeline --as-of 2026-10-26 --output-dir artifacts
```

## Единица наблюдения и выборки

Одна строка ML-выборки соответствует одной сделке `price_id`. `dataset.sql` берёт
города из `core.dim_cities`, где уже оставлен минимальный исходный `cities.id` на
`gc_id`. Полное название разделяется по первой запятой; город и регион отправления
и назначения образуют четыре независимых категориальных признака. При отсутствии
региона используется постоянная категория `Не указан`.

Связь сделки с несколькими группами кузова сворачивается в отсортированную строку,
например `Борт | Тент`. Сделка остаётся одним наблюдением, поэтому перевозки с
несколькими допустимыми кузовами не получают повышенный вес. Дополнительно используется
стандартизированная основная группа из `prices.body_type`: набор совместимых кузовов
и основной кузов несут разную информацию. Если основной тип и таблица связей
противоречат друг другу, оба источника сохраняют свой смысл; ML не назначает приоритет
кузову по величине цены. В данном генераторе противоречивые случаи специально не
размечены, поэтому отдельная проверка согласованности этих полей — дальнейшее улучшение.

| Выборка | Дата погрузки | Правила |
| --- | --- | --- |
| train | `2026-07-26 <= loading_date < 2026-10-05` | Валидный факт, `price_type` из `1,2,3,4,5,9`, прямой маршрут, `outlier_mark=false` |
| test | `2026-10-05 <= loading_date <= 2026-10-26` | Те же условия, что для train |
| future | `loading_date > 2026-10-26` | Любая прошедшая DQ простая заявка из core, включая аукционные; заполненный `price` не считается фактом |

Границы считаются от переданного `as_of`: три календарных месяца и три недели.
Системная дата не меняет результат. Все выборки сортируются по дате погрузки и
`price_id`. Сортировка не смешивает train и test.

## Признаки и защита от утечек

Модель принимает только `FEATURE_COLUMNS`, явный список из `ml/features.py`:
расстояние, вес, объём, четыре координаты, год, шесть синусных/косинусных компонент
месяца, дня недели и дня года, два города, два региона, группы кузовов, весовую и
объёмную категории. Для периодов используются `12`, `7`, `365.25`; положение в цикле
начинается с нуля.

В признаки не входят идентификатор сделки, цена, её производные, роль организации,
выручка/маржа, `outlier_mark`, `price_group_id` и статистики текущего месяца. Набор
признаков не меняется при добавлении этих полей в исходный DataFrame. Это проверяется
тестом, который подменяет целевые и потенциально опасные поля.

Числовые пропуски обрабатывает CatBoost, категориальные заменяются постоянной строкой.
Здесь нет обучаемого на полном датасете заполнения пропусков, масштабирования,
дополнительного отсечения выбросов или кодирования по целевой переменной.
Категориальные статистики и деревья обучаются только на train. Модель получает
`has_time=True` и `boosting_type="Ordered"`; CatBoost использует порядок входных
наблюдений. Параметр `has_time` описан в
[официальной документации CatBoost](https://catboost.ai/docs/en/references/training-parameters/common#has_time).

Гиперпараметры заданы заранее: RMSE, 500 деревьев глубины 6, темп обучения 0.06,
CPU, 2 потока, фиксированное зерно. Test не используется как `eval_set`, для ранней
остановки, выбора числа деревьев или подбора параметров. Тариф моделируется прямо
в рублях без НДС; логарифмирование целевой переменной не применяется. Прогноз
ограничивается снизу значением `0.01` рубля — фиксированное правило допустимого
диапазона, не вычисляемое по отложенной выборке.

## Воспроизводимость, артефакты и запись результатов

`model_id` зависит от train-данных, параметров, `as_of`, кода признаков/запроса/пайплайна
и версий библиотек. Изменение будущей заявки или таргета отложенной выборки не переобучает
модель. Если файл модели с тем же идентификатором уже существует и его SHA-256
совпадает с манифестом, модель загружается из файла. Это делает повторный запуск
быстрее и сохраняет байты артефакта. При изменении обучения создаётся новая версия.

В `output_dir` появляются:

| Файл | Содержимое |
| --- | --- |
| `models/<model_id>/model.cbm` | Модель CatBoost, доступная для повторного применения |
| `models/<model_id>/manifest.json` | Код, состав признаков, настройки, версии, хеш train и SHA-256 модели |
| `ml_manifest.json` | Манифест модели последнего успешного запуска |
| `ml_metrics.json` | Фактические R², MAPE в процентах, RMSE/MAE в рублях, границы и объёмы выборок, ограничения |
| `ml_feature_importance.csv` | Важность признаков обученной модели |
| `ml_predictions_sample.csv` | По 20 примеров test/future для быстрой проверки |

Полный результат сохраняется в PostgreSQL: реестр `mart.ml_models`, оценки
`mart.ml_evaluations` и витрина `mart.ml_price_predictions`. Ключ витрины —
`(as_of, price_id)`. Это одна строка на сделку в конкретном снимке; разные даты
снимка допускаются и не являются дублями. Данные передаются одной командой `COPY`
через временную таблицу, затем публикуются одной транзакцией. Изменённые строки
обновляются, неизменённые сохраняют `scored_at`, а строки, которых больше нет в
выборке данного снимка, удаляются. История других снимков сохраняется.

Будущие `actual_price_rub`, `abs_error_rub` и `ape_pct` заменяются на `NULL` в SQL-запросе,
после разделения выборки и перед записью. Ограничение таблицы дополнительно запрещает
сохранение таких полей для future. Метрики вычисляются только по test. Общая advisory
блокировка `smart_logistics.pipeline` не допускает изменения core/mart другим
запуском конвейера во время обучения и публикации.

## Практические границы результата

1. Набор включает тарифы разных ролей: заказчиков, экспедиторов и перевозчиков.
   Это следует обязательному фильтру задания, но не позволяет интерпретировать
   результат как чистую экономическую себестоимость перевозчика. Для такой задачи
   нужно отдельно согласовать и проверить выборку типов `3/9`.
2. Новые записи за `2026-10-26` могли не пройти ночную разметку выбросов. При
   `outlier_mark=false` они остаются в test; возможное ухудшение метрик не скрывается
   дополнительным удалением наблюдений отложенной выборки.
3. Скоринг строится поверх прошедших DQ строк `core`. Будущие заявки с невалидной
   ценой или отсутствующим курсом находятся в карантине и не получают прогноз.
   Для рабочего сервиса заявок без известной цены нужен отдельный входной контракт
   качества признаков, не зависящий от наличия таргета.
4. Трёхмесячное окно почти целиком охватывает один сезон и один год. Наличие
   календарных признаков само по себе не доказывает способность модели точно
   прогнозировать весь год или инфляционный тренд. Прогнозы дальних будущих заявок
   требуют последующей проверки на реальных фактах.
5. Это проверка на фиксированном снимке данных. Исходник не хранит историю версий
   ставок, кузовов и ночных флагов; восстановить значения, известные строго в каждый
   момент прошлого, по такому снимку невозможно. Никакие агрегаты test/future при
   обучении не используются, но полноценная проверка доступности данных во времени
   потребует истории изменений в источнике.
